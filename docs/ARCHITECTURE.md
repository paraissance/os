# JodyOS architecture

This document answers the brief's first task (inspect and report) and describes what Phase 1 built.

## 1. What existed

`github.com/paraissance/os` was created empty on 2026-10-08: no commits, no files. Everything here is new. Nothing was overwritten.

## 2. Stack

| Layer | Choice | Notes |
| --- | --- | --- |
| Framework | Next.js 16.4 (App Router, Turbopack) | Cache Components and Partial Prefetching on: each page ships a static shell instantly and streams private data behind `<Suspense>`. |
| UI | React 19.3, TypeScript 5, Tailwind CSS 4 | Black and white, soft: Archivo for text, soft grey cards with rounded corners instead of outlined boxes, pill buttons and tabs, no icon library. Short CSS animations (rise, grow, slide, count-up) that switch off under reduced motion. Tokens and keyframes in `src/app/globals.css`; component kit in `src/components/ui`. |
| Database | PostgreSQL via Drizzle ORM 0.45 | SQL migrations generated by drizzle-kit into `drizzle/`. |
| Local / test DB | PGlite (Postgres compiled to WebAssembly) | Same engine as production, no install. Tests run against an in-memory instance. |
| Business data | JodyOS's own database | Edited in JodyOS; optional live numbers from the OS Analytics WordPress plugin 1.3.0+. See "Businesses" below. |
| Validation | Zod 4 | Every Server Action, Route Handler and the environment. |
| AI | Anthropic TypeScript SDK | Behind a provider interface (`src/lib/ai/types.ts`), so OpenAI and others plug in without touching the app. |
| Tests | Vitest 5 | 88 tests: unit, database, the chat API end to end and the plugin contract. |
| Hosting | Vercel + GitHub | CI on GitHub Actions. |

Two additions to the brief's stack, each for a concrete reason:

- **PGlite for local development and tests.** Real Postgres with nothing to install on Windows, and tests that exercise real SQL (constraints, upserts, cascades) instead of mocks.
- **Hand-rolled auth instead of a framework.** JodyOS has exactly one owner. Opaque session tokens stored hashed in Postgres, scrypt passwords and a setup token cover it with no extra dependency, and every session can be listed and revoked. OAuth providers can be added later if a team ever needs access.

## 3. Architecture

```
Browser
  │  proxy.ts: no session cookie → /login (optimistic, never the real check)
  ▼
Page = static shell (layout, nav, headings) + <Suspense> sections
  │  each section: requireUser()  ← Data Access Layer: validates the session in Postgres
  ▼
src/lib/*  (activity, settings, chat, rate-limit, auth, integrations)
  ▼
Drizzle ─► PostgreSQL (Neon in production, PGlite locally)

AI Command:  POST /api/chat → origin check → session → rate limit → zod
             → ChatProvider (Anthropic) → NDJSON stream to the browser
             → message saved → activity_logs entry
```

### Businesses

Every business is stored in JodyOS's own database and edited in JodyOS (`/businesses`): its details and "about" text, websites (domain, hosting and SSL dates, registrar and hosting accounts and login pages; never passwords), links (pages, social, logins, tools), common questions, and subscriptions (per business, or shared by all). Tables: `businesses`, `business_links`, `business_faqs`, `business_sites`, `subscriptions` (migration `0001_businesses`).

- `src/lib/business-input.ts`: the zod rules for everything the owner types or imports. Blanks become null; web addresses get `https://` when missing and must be http(s); domains are normalised; dates must exist; prices are read the way people type them.
- `src/lib/businesses.ts`: database access. `loadBook()` reads the five tables once per request. Writes are single statements; import is one transaction.
- `src/lib/business-model.ts`: pure derived values: renewals and how soon they're due (warning 30 days ahead), monthly costs by category, what needs attention, grouped links, what's coming up.
- `src/app/actions/businesses.ts`: Server Actions. Each re-checks the session, validates, logs to the activity trail and refreshes the page.
- **Import and export** (`/businesses/import`, `GET /api/businesses/export`): one JSON format (`"format": "jodyos-businesses", "version": 1`). Import matches businesses by slug: new ones are added; for existing ones, the details are updated and their links, questions, websites and subscriptions are replaced. Shared subscriptions are replaced only when the file lists them. Export writes the same format, so a backup restores exactly (tested).

**Dashboard tabs.** The dashboard (`/`) has an "All businesses" tab and one tab per business (`/?b=<slug>`). Each business has Summary, About, Links, Money and Website sections (`&s=<section>`), each opening with a plain sentence, with an Edit shortcut to the matching part of the edit page. All sections render on the server and switch instantly on the client; the URL is updated in place. Switching business keeps the open section. `/businesses/<slug>` redirects to the tab.

### Live numbers (optional): OS Analytics

When `OS_ANALYTICS_URL` and `OS_ANALYTICS_KEY` are set, the OS Analytics WordPress plugin (1.3.0+) adds live numbers on top, matched by slug: leads, pipeline, funnel, appointments, social, posts, campaigns and tasks. Businesses then also get Marketing and Leads sections, and "needs attention" adds lead drops, overdue tasks and failed posts. Without it, everything else works.

```
JodyOS server  ──GET + X-OS-Key──►  WordPress  /wp-json/jdy/v1/os/businesses
               ◄── JSON (zod-validated) ──      /wp-json/jdy/v1/os/businesses/{slug}
```

- Read-only, three GET routes. One key, generated on the plugin's Settings → JodyOS connection card, shown once and stored there only as a SHA-256 hash. Ten bad keys lock that IP out for 15 minutes.
- Never sent by the plugin: lead emails, phone numbers, IP addresses, browser details, raw form data, passwords or API keys.
- Fetched at request time (no cache, 10-second timeout) and validated; every link is checked to be http(s). An outage shows a short note; it never hides a business.
- The contract is tested on both sides: the plugin's PHP harness writes its real JSON to `tests/fixtures/`, and JodyOS's tests parse exactly that.

The brief's target shape, `JodyOS → AI Orchestrator → Tool Registry → Integrations / APIs / MCP → External Services`, starts in Phase 2. Phase 1 put the seams in place: the provider interface, the activity log (with columns for request, AI decision, tool, result, status and error) and the module registry (`src/lib/modules.ts`) that drives navigation and placeholders.

### Security in Phase 1

- **Authentication:** owner account created once at `/setup`, gated by `SETUP_TOKEN` (constant-time compare, rate limited, advisory lock so only one owner can ever be created).
- **Passwords:** scrypt with N=2^17, r=8, p=1 (OWASP), per-hash salt, parameters stored with the hash. Unknown emails still run a full hash, so timing doesn't reveal which accounts exist.
- **Sessions:** 256-bit random token in an `httpOnly`, `SameSite=Lax` cookie, `__Host-` prefixed and `Secure` in production. Only its SHA-256 is stored. 30-day expiry, listed and revocable in Settings; changing the password signs out every other device.
- **Authorization:** every Server Component section, Server Action and Route Handler re-checks the session. Conversation queries always filter by owner.
- **Rate limiting:** stored in Postgres, so it holds across serverless instances. Sign-in: 10 per IP and 5 per email per 15 min. Setup: 5 per IP. Password change: 5 per user. Chat: 20 per user per minute.
- **Input validation:** Zod on every input. The chat API also rejects cross-origin requests.
- **Secrets:** environment only. Activity-log metadata passes through a redactor (password, token, key, secret, cookie, session and authorization fields), and provider errors are scrubbed of anything key-shaped.
- **Headers:** `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `nosniff`, a strict referrer policy, a Permissions-Policy, and `noindex` (plus `robots.txt` disallow).
- **Errors:** users see a generic message plus a reference digest. Details stay in server logs.
- **AI honesty:** the system prompt tells Jody Core it has no tools in Phase 1 and must never claim to have checked, posted or changed anything.

## 4. Database

Phase 1 tables (`src/lib/db/schema.ts`, migration `drizzle/0000_init.sql`):

| Table | Purpose |
| --- | --- |
| `users` | Owner account (email unique, scrypt hash, role). |
| `sessions` | Hashed session tokens with expiry, last seen, IP and user agent. |
| `activity_logs` | Audit trail: actor, action, request, decision, tool, result, status, error, metadata. CHECK-constrained status and actor. |
| `settings` | Key/value JSON (time zone, model, effort, standing instructions). |
| `rate_limits` | Fixed-window counters. |
| `conversations`, `messages` | AI Command history, per user, with model, stop reason and token counts. |

Added in the phase that needs them, each as a new migration: `projects`, `tasks`, `memories`, `permissions` (Phase 2); `websites`, `social_accounts`, `integrations` (Phase 3); `automations`, `notifications` (Phase 4); `agents` (Phase 5).

Workflow: edit `schema.ts`, run `npm run db:generate`, review the SQL, commit it. Vercel applies pending migrations at build time (`npm run vercel-build`). Locally, PGlite migrates itself on first use.

## 7. Vercel plan

- **Project:** import `paraissance/os`. `vercel.json` runs `npm run vercel-build`, which applies migrations and then builds.
- **Database:** Neon Postgres from the Vercel Marketplace (sets `DATABASE_URL`; enable preview branches so preview deployments never touch the production data).
- **Environment:** `SETUP_TOKEN` (remove after setup) and `ANTHROPIC_API_KEY`, for Production and Preview.
- **Runtime:** Node.js 22. The chat route allows up to 300 s for long answers.
- **Plan:** Vercel's Hobby tier is for non-commercial use. Running your businesses through JodyOS needs Pro.
- **Domain:** add a custom domain when ready. Nothing in the app assumes one.

## 8. GitHub workflow

- `main` is production. Work on a branch, open a pull request, merge when CI is green; Vercel builds a preview for every branch.
- CI (`.github/workflows/ci.yml`): lint, type check, tests and a production build on every push and pull request.
- One logical change per commit. Schema changes ship with their migration.
- Secrets are never committed: `.env*` is ignored except `.env.example`.
- **The repository is public.** Code alone holds no secrets, but for a private operating system it should be made private (GitHub: Settings > General > Danger Zone > Change visibility).

## 9. Phase plan

1. **Foundation (done):** Next.js app, design system, dashboard, navigation, auth, database and migrations, settings, activity log, basic AI chat, environment config, CI, deployment config.
2. **Jody Core (next):** provider abstraction with OpenAI, command processing, planner, tool registry (name, description, input/output schema, permissions, auth requirements, error handling), permission engine (READ runs automatically, WRITE follows rules, DESTRUCTIVE always asks), execution engine with verify and log steps, basic memory. Tasks becomes a real module, and Jody Core gets read access to Businesses.
3. **Integrations, one at a time:** GitHub, Vercel, WordPress, Blotato, Google Analytics 4.
4. **Automation:** scheduler (Vercel Cron), recurring and conditional tasks, monitoring, notifications, run history.
5. **Agents:** SEO, Website, Social, Analytics, Content and Reporting, all through the same tools, permissions and logs.
6. **Advanced:** MCP servers as tools, richer memory and RAG, multi-agent, voice, mobile, proactive insights.
